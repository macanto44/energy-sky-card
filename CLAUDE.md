# CLAUDE.md

Map of the code for Claude Code and anyone working here.

## The project

Energy Sky Card is a Home Assistant dashboard card (Marketplace / HACS category "Dashboard", `plugin`) that shows solar production, battery and grid on a background carrying information, chosen by `background`: the weather, one colour, or the day's tariff colour (EDF Tempo's, or any tariff sensor's) by day, a starry sky by night. Tempo is one sky among three, not the card's premise: keep it that way in public texts. Specification: `BRIEF-energy-sky-card.md` (kept local, not committed; the source of truth, in French).

## Commands

```bash
npm install
npm run build        # the two bundles, written to the repository root
npm run dev          # rebuild on change
npm run type-check   # tsc --noEmit, strict
npm test             # Vitest, once (build first: test/build.test.ts checks the bundle)
npm run test:browser # headless Chrome: animations pause off-screen, none under reduced motion, no overflow, sky off text (also in CI)
npm run screenshots  # the README's pictures in docs/images/, in English: 3 day stills, cote.png (side), cote-flux.png (side with flow and appliances), nuit-anim.png and flux-anim.png (the night and the flow, animated PNGs)
npm run test:coverage
```

## How it ships

- **Two bundles**, IIFE, minified, es2020 (`esbuild.config.js`):
  - `energy-sky-card.js`: the card, the only dashboard resource. Budget: < 33 KB gzip (tested; 30 until the 0.4.0 sky). `esbuild.config.js` strips the stylesheet's comments and indentation (`cssComments`: from `CARD_CSS` on in `src/styles/card.ts`): explain the CSS in comments freely.
  - `energy-sky-card-editor.js`: the visual editor, loaded the first time the editor opens (`loadEditorBundle` in `src/bundles.ts`, which keeps the `?v=` / `?hacstag=` cache buster).
- **The name** lives in `src/constants.ts` (`CARD_NAME`). `esbuild.config.js` reads it from there to name the bundles. The version comes from `package.json` (`__VERSION__`).
- **No runtime network requests, no GSAP, no `@mdi/js`.** Icons are `<ha-icon>`.
- Bundles are committed (installs from the branch get them).

## Releases

- `CHANGELOG.md`: a line per user-visible change.
- Release: bump `version` in `package.json` (and the `?v=` in the README), `npm run build`, commit, then push a tag `vX.Y.Z`. `.github/workflows/release.yml` checks the tag matches, builds, tests and publishes a release with the two bundles attached, which is what the Marketplace / HACS install (`hacs.json` → `filename: energy-sky-card.js`).
- `.github/workflows/ci.yml` fails if the committed bundles don't match a fresh build: commit the rebuilt files with every source change.
- `.github/workflows/validate.yml` runs HACS's validation (category `plugin`).
- `.github/workflows/pages.yml` publishes the live demo (`demo/live.html` on the built card) to GitHub Pages once the Release workflow succeeds (`workflow_run`: the `github-pages` environment deploys from `main` only, so not on the tag itself), or by hand: https://macanto44.github.io/energy-sky-card/

## Behaviour notes

- Outage: `gridOutage` makes `flowView` treat the grid as 0 W and its node `alert` (`data-alert`: red border, `alert` ring, value « Coupure »).
- Smoothing: with `smoothing` > 0 (s) the card records each power entity's readings (`smoothedEntities`: production, home, battery, grid, appliances) and renders from `shown`, a copy of hass with their averages as states (buildView, flowView, the sky); stale detection reads the raw hass. The averages shown are worked out every `REFRESH_MS` (5 s, or the window if shorter) and held in between (`Smoother.smoothed`): hass comes several times a second, and averages redone each time crept towards each reading like lag. A sensor with readings but no held average (first one, back from unavailable) brings the refresh forward; an unavailable one shows its own state. A 1 s tick while connected re-renders when the held averages' 3 significant digits change. A reading counts once (by `last_updated`); unavailable or a new unit starts the average again.
- Stale readings: `staleReadings` (model.ts) lists the measures (powers, charge, temperature, voltage, free cells, appliances) whose `last_reported` is `stale_after` minutes old (`DEFAULT_STALE_MINUTES` 30; 0 off). Never `last_updated`: it only moves on a change, so an idle 0 W would look stale; without `last_reported`, nothing is flagged. `markStale` (each update, and every minute by `staleTimer` while connected): a cell's `ha-icon` becomes `mdi:clock-alert-outline` (its own icon kept in `data-icon`), `data-stale` and a title with the age; a flow node gets `data-stale` (dashed border) and the title.
- An unavailable daily sensor is left out of the sum; with none available the line reads "— kWh produits".
- The battery complement « · SOC atteint » shows when any `battery.soc_reached_entities` entity is on; nothing otherwise. The older names (`battery.lock_entities`, top-level `power_threshold`, `cell_tap`) are gone: `validateConfig` rejects them with the name that replaces them (`RENAMED`).
- `battery.temperature_entity`: the temperature follows the charge in the battery value (« 78 % ↑ · 24 °C », the sensor's unit, rounded); left out without a reading.
- Battery estimate (`batteryEstimate`, model.ts): with `battery.capacity`, the time to `max_soc` (charging) or to `reserve_soc` (discharging) at the battery power's moving average over `estimate.average` minutes (`DEFAULT_ESTIMATE_AVERAGE` 5; `estimateAverageMs`), the card's own `estimateSmoother` whatever `smoothing` says, or the raw reading with `average: 0`; passed to `buildView` / `flowView` as `ViewOptions.estimatePower` with `now`. The window is filled from Home Assistant's history (`pastReadings`: `history/history_during_period`, then `Smoother.seed`) once per config and per connection (`historyRead` drops an answer for an older one). `viewEstimate` shows nothing while the present power is idle or of the other sign than the average. Rounded to `ESTIMATE_STEP` (10 min; a clock time on the step), none when idle, beyond 24 h, there already, or while `soc_reached` (`viewEstimate`). `estimate.charge` / `discharge` choose `time` / `duration` / `off`, `with_temperature` `replace` (default) or `both`. The cell: in its value (and tight / bare forms), the sentence as `MetricView.note` in the title; the flow: `NodeView.sub`, the sentence as a third small line `.nsub` under the battery node's power, `subShort` (« → 100 % 14:20 », `BatteryEstimate.target`) where it doesn't fit; `fitSub` (each update and in `fit()`) tries both, then both at `data-tight` (9 px), else the narrower; `note` in its title (`data-note`), unless `estimate.flow: false`. The render key carries the minute. Standard layout: when the tight form still overflows (a 12 h clock), level 3 (no complement) before the ellipsis. Editor: `estimate_*` fields in the Battery block's « Time to full / empty » section (`estimate_power`: `average` / `instant`, form-only, instant written as `average: 0`), shown with a capacity (a list of capacities stays YAML-only), written under `estimate` only where not the default.
- Power entities in kW / MW and energy entities in Wh / MWh are converted from their `unit_of_measurement`.
- Grid and battery power: one signed sensor (`power_entity`, `invert`) or two positive ones (`grid.import_entity` / `export_entity`, `battery.charge_entity` / `discharge_entity`; `gridPower` / `batteryPower` take in − out as magnitudes, a missing one as 0); both forms at once is a config error (`SPLIT`). The battery's options take lists (several batteries): powers summed, `batterySoc` averages the charge, weighted by `battery.capacity` when it is one per battery. Always go through `batterySocEntities`, `batteryPowerEntities`, `gridPowerEntities` (model.ts), never the raw options. Editor: a `sensors` choice (`single` / `split`) per block, form-only, dropped by `nextConfig` with the other form's fields; one battery saved as a string.
- `production_entity` is a string or a list (summed by `productionPower`, used by the hero, the halo and the flow; below `production_threshold`, if set, it reads 0). `grid.invert` / `battery.invert` flip the sensor's sign (`gridPower`, `batteryPower`).
- Cells (`configuredCells` in model.ts): `cells` if set (≤ 4, built-in kinds deduplicated, free cells keyed `custom-<index>`), else the built-in ones whose entities are set. A free cell's name and icon are user text: written with textContent / setAttribute only. The editor shows them as four slots (`cell_1` … `cell_4`, plus `_entity` / `_name` / `_icon` for a free one) and writes `cells` only when they differ from the automatic choice.
- Cell taps: a cell's own `tap_action` (`{ type, tap_action }` for a built-in cell, `tap_action` on a free one; `CellSpec.tapAction`), else its entity's more-info unless the card has a `tap_action`. Such cells get `data-cell-target` (role button and tabindex unless their action is `none`). The gesture listener passes the event path to `actionsFor`, which answers with the cell's entity and its tap (hold / double tap stay the card's). Editor: `cell_n_tap_action` slots (ui_action), a built-in cell saved as an object only when it has one.
- `getStubConfig` is async (HA awaits it): `stub.ts` reads `energy/get_prefs` in both shapes (grid `flow_from[]` / `power[]`, or `stat_rate` / `power_config`), takes sensors on the meters' devices from `hass.entities`, and sets `battery.invert` when the power is HA's `stat_rate` (positive discharging).
- Self-sufficiency cell (`self_sufficiency`, no entity): the card reads `energy/get_prefs` and each meter's `change` since midnight (`recorder/statistic_during_period`, `calendar: day`), 5 min apart or just after midnight (`nextRefreshIn`), only while a cell shows it and connected; `selfRead` drops an answer for an older config. The sum is the Energy dashboard gauge's: `1 − min(1, bought / used)`, used = the home meter, else bought + solar + discharged − sold − charged. Passed to `buildView` as `ViewOptions.selfSufficiency`; « — » until read. Tap: `/energy` unless the cell has its own `tap_action` or the card a `tap_action`. The editor offers it when the dashboard has a grid meter (asked once), or when a cell already shows it.
- An appliance's charge (`consumers[].soc_entity`, `ConsumerView.soc`): the ring shows it in the battery's colour (`batt`) and the disc its number (`data-centre`), in place of its share of the home; the title (`data-title`, which `markStale` builds on) and aria-label add it. `always_show` keeps it `shown` below the threshold. Editor slots `consumer_<n>_soc_entity` / `_always_show`.
- `night_hero` (consumption / battery) only applies below the horizon and when its entity is set; the context line then starts with the hero's name, shortened when too wide (`data-short-context`).

## Sizing

`getGridOptions()` → 12 × 4 (248 px), min 6 × 3. Default spacing copies the prototype's (roomy, grid anchored to the bottom). One `fitLayout()` serves both layouts (on resize via ResizeObserver, and when the text that decides the layout changes): for the roomy then the compact spacing (`data-compact`, 3 rows / 184 px), for each level of the cells' text, for each hero size (`data-hero`), the first where the hero line and the content don't overflow, the cells' lines too in standard. The text levels (`metricForm` in model.ts, `data-form` on the host when above 0): 0 in full, 1 the short complement (« SOC atteint » → « SOC ✓ »), 2 the tight form where a cell has one (`MetricView.tight`, the battery with a temperature: « 100 % ↓ · -13° ✓ », narrow spaces), 3 no complement (`MetricView.bare`, « 78 % ↑ », side only). The card writes one text per cell (`writeForms`); nothing is stacked and hidden in CSS. In standard, lines still too wide take level 2 and end in an ellipsis; a context line too wide takes its short form (`writeContext`, `data-short-context`). `npm run test:browser` checks that nothing overflows at 304 px (a 320 px phone) in every language, extreme values included.

### Side layout

`layout: side` (`data-layout="side"` on the host; `getGridOptions()` → 12 × 2, min 6 × 2; `getCardSize()` 2): the same DOM, laid out by CSS as a two-column grid (hero and context on the left, the cells' `.grid` on the right, `max-content` wide, a hairline on its left). Each cell is icon + value; `.label-text` is visually hidden (screen readers), the cell's `title` is its label. The day sky is the gradient from `SIDE_SKY_FROM` (0.45) down (`sideGradientAt`; a `color-mix` first stop), and the halo is `SIDE_HALO`, a 100 px circle centred 30 px above the top left corner: the values reach the card's top, where the full gradient or the usual halo would fail 4.5:1. `fitLayout()` here goes through levels 0–3 and hero sizes 44 / 40 / 36, and the context line shares the left column with the hero: in full on one line, else short on one line, else in full on two lines (line-clamp 2), short if two are too few. `npm run test:browser` checks side cards at 304 / 360 px (`demo ?side`, a 120 px cell).

### Expandable

`flow: tap | always` (0.3.3's `expandable: true` is read as `flow: tap` by `validateConfig`, and saved as `flow` by the editor). `data-flow` on the host, `data-expanded` while the flow shows; `card.expanded` gets / sets it (always true with `always`, set in `setConfig`). With `tap` only: the grabber, and the hero, the context line and the `.panel` carry `data-cell-target` + `data-target-key="toggle"`; `actionsFor` answers them with `toggle` (actions.ts: a tap runs it instead of an action; hold and double tap stay the card's). The hero is the keyboard button (`aria-expanded`). Nodes with an entity (`flowNodeEntity`) open it (key `node:<name>` in `cellTargets`). The card sets its own height: `getGridOptions()` → rows `'auto'`, `.content` is `--esc-top-h` (248 / side 120 px), `.sky` stays that tall (so the gradient, halo, clouds and stars and their contrast tests are unchanged) and the panel sits on `--esc-floor` (`floorRgb`: the sky's last colour, day over night by `--esc-day`, set by `paintHeavens`), with dawn and dusk carried on below the seam by `.floor` (`floorGlowAlpha` / `floorGlowRgb`, gone `FLOOR_GLOW.end` px down, above the wires' crossing); the nodes' glass fades with `--esc-twilight` so their text keeps 4.5:1 (flow.test.ts, along the sun's course on every sky). The panel (`FLOW_HEIGHT` 220 px): an SVG of wires (paths drawn for the panel's width by `layoutFlow` in `fit()`: `sh` and `gb` straight, the four others S curves between facing edges, `WIRE_INSET` in from a node's end, so the corners stay free, with one `@keyframes esc-flow-<wire>` each in a `<style class="flow-keyframes">`, transform + opacity only) under four HTML nodes. Appliances (`consumers`, ≤ `MAX_CONSUMERS` 4): one below `consumer_threshold` (`DEFAULT_CONSUMER_THRESHOLD` 10 W; 0 shows all) or without a reading is out of the flow (`shown`): `updateFlow` hides it at once, and when the set of shown ones changes the corners are laid out again for those only (`shownConsumers`, each wire's `--esc-flow` set to its place's keyframes). `flowView` gives each its label (name, else friendly_name, else the entity), icon (else the entity's, else `CONSUMER_ICON`), power, `share` of the home and level; `flowGeometry(width, n)` places them in the right corners (i even above the home, odd below): whole nodes when there are ≤ 2 and the corner is ≥ 110 px, else compact (`data-compact` on `.flow`, `COMPACT_WIDTH` 46, name hidden, `title` and `aria-label` carry it), one per corner under 100 px (a phone: the first two). Their wires (`c0`…`c3`, class `use`, keyframes `esc-flow-c<n>`) run from the home; nodes `data-consumer`, `data-idle` under 20 W (the disc dims, the text doesn't), taps via `cellTargets` `consumer:<i>`. Editor: the « Appliances » block (always there for `consumption_entity`; the appliances' fields with a flow), slots `consumer_<n>_entity` / `_name` / `_icon` / `_tap_action`, each slot after a filled one. `energyFlows` balances like the meters (sales: sun, then battery; charge: sun, then grid; the home the rest; each source hands out exactly its power, tested); `flowView` zeroes a battery within `battery.power_threshold`. The grid ↔ battery link (`gb`, dotted while idle; `bg` drawn only while selling, same line) runs down the middle under `sh`, whose `.gap` path in the panel's colour (`--esc-panel`) bridges it. Height: `flowGeometry` returns `height` = 65 % of the width (`FLOW_ASPECT`), between `FLOW_HEIGHT` 220 and `FLOW_MAX_HEIGHT` 360; `layoutFlow` sets it as `--esc-flow-h` (the nodes' rows follow in CSS) and the SVG's viewBox. Colours: `FLOW_COLOURS` (sky.ts, so the editor bundle doesn't pull the CSS) are the defaults of CSS variables (`FLOW_COLOUR_VARS`: `--energy-sky-card-solar` / `-grid` / `-battery` / `-consumption`) that a theme sets for every card; `flow_colors` in the config sets them on the host; the editor shows `color_rgb` pickers (`flow_color_<key>`, Layout block, with a flow), writing a hex only when it differs from the default and leaving a non-hex YAML colour alone. Wire levels 0–4 (`flowLevel`) set width, comet count (1 / 2 / 3) and speed in CSS; comets animate only under motion on / paused, unfolded, on a non-idle wire. The editor turns a numeric `grid_options.rows` into `auto` when `expandable` is set. `npm run test:browser` checks unfolded cards in both layouts (`demo ?expand`).

## The real sky (0.4.0)

`celestial()` (celestial.ts) reads `sun.sun`'s `elevation` / `azimuth` (else works them out from `hass.config` latitude / longitude, astro.ts); without either, the old day / night by `sun.sun`'s state. `paintHeavens` (card) sets `--esc-day` (the day layer's opacity over the night layer: 1 above 5°, 0 below -4°; `data-mode` still says day / night for the animations and the night hero), `--esc-stars` (stars' opacity factor: out from -1° to -8°, paled by the moon), `--esc-twilight` (the `.tint` glow, `twilightStrength` × the weather's `GLOW_THROUGH`; `data-dawn` before the sun's culmination, its hour angle (`hourAngle`, from elevation / azimuth / latitude): rose, else amber; none on a solid sky), the sun's look (`--esc-p` production share, `--esc-warm` / `-bloom` / `-core` / `-rim` / `-edge` warming as it sinks, `--esc-flat`, `--esc-sun-scale`, `data-rays` 6 / 12 in a clear sky above 8°), the moon (`moonMarkup` SVG of its phase, redrawn when the lit share changes by 0.01; `--esc-moon-r` turns its lit side to the sun: `limb` bearing - 90, mirrored south of the equator), the wind (`windAcross`: `--esc-rain-dx` / `-rot`, `--esc-wind-dir` for the clouds), the rainbow (`data-rainbow`, ten minutes after a rainy state turns sunny / partly cloudy / windy, the sun below 42°; the sun hides meanwhile, being behind you) and `data-golden` (self-sufficiency ≥ 99.5 %). The sun shows on Tempo and on sunny / partly cloudy / windy weather; the moon needs `hass.config` and a sky that isn't overcast, is pale by day only when well away from the sun (elongation > 50°, lit > 25 %). `arcPlace` gives the sun's and the moon's place along their arc of the day (hour angle over the half-arc above the horizon: 0 rising, 1 setting, at any latitude and season; the azimuth alone parked a summer sun on an edge and made it jump south of the equator). `placeSky` (each paint and in `fit()`) maps that and low → high to a zone in the top right (right of the hero), then moves the sun or the moon up, then right, until it is `SUN_CLEARANCE` px from the hero (52), the context line (86) and the cells (86), hiding it without room; the rainbow keeps right of the hero and fades out above the context line. The glow and bloom (`SUN_GLOW`, `SUN_BLOOM`, linear discs), `MOONLIGHT` and `TWILIGHT` are tested for contrast at those distances on every palette (sky.test.ts). Standard layout only: the side layout keeps its halo. Repainted every minute (the stale timer). The demo fixes its clock at `MOMENT` (?at=…, `at=now`), gives each scenario `sun.sun` attributes (`SUN`) and the night ones a place (`placeFor`); `soir` is a sunset.

## Motion

`data-motion` on the host: `on`, `paused` (tab hidden or card off-screen, 100 px margin) or `off` (`animate: false` or `prefers-reduced-motion`). CSS declares animations only under `on` / `paused`; the play state goes through `--esc-play`, because the `animation` shorthand resets a separate `animation-play-state` rule (jsdom can't see that: `npm run test:browser` checks it in Chrome). The halo breathes (3 s alternate = 6 s cycle, opacity ×0.55 ↔ ×1 and 12 % larger at the peak: it breathes down, never above its alpha, to keep the hero's contrast) only by day with production; stars twinkle (2 s alternate = 4 s, opacity ×0.15 ↔ ×1 of the star's own `--esc-o`, scale 0.6 ↔ 1.4) and three shooting stars pass (top right / top left / across the middle, every 11 / 17 / 23 s, each pass the first 8 % of its period) only at night; by day three cloud shadows (dark navy, at most `CLOUD_MAX_ALPHA` 0.2) cross the card (`esc-drift`, a card-wide `.drift` from -110 % to 110 %, 47 / 61 / 73 s): they only darken, so the contrast can only rise (`sky.test.ts` checks it). Stars cover the whole card: `clearText()` (end of `fit()`, and once fonts load) hides each one whose reach (radius at its peak + 3 px) would touch a word, an icon or the hairline; `test:browser` checks none touches text and every quarter has some. Day dots were tried in 0.3.0 and dropped: small bright dots read as stars. The day/night cross-fade (3 s) starts after the first paint (`data-ready`).

### Skies

`background`: `tempo` (default), `solid`, `weather`; `computeBackground` (sky.ts) returns `sky`, the day `palette`, a `nightPalette`, and for the weather its `WEATHER` key. `solidPalette` darkens `background_color` step by step until `textContrast` (white text where it sits, sky.ts) reaches 4.6. `WEATHER` holds each condition's day / night palettes, clouds (count, alpha by day / night, windy), rain, snow, fog, flash, halo and stars (`all` / `few` / `none`); `weatherKey` maps Home Assistant's other conditions (clear-night → sunny, hail → pouring, windy-variant → windy, exceptional / unknown → cloudy). The card sets `data-sky`, `data-stars`, `--esc-n0…2` (the night layer, the card's and the flow panel's night colour) and `--esc-cloud-a`, and redraws `.wx` (weatherMarkup) only when the condition changes. Weather animations (cloudband drift, esc-rain, esc-snow, esc-fog, esc-flash) follow the motion rules; drops and flakes only show while falling. The Tempo sky's cloud shadows (`.drift`) hide under the weather. Side layout: clouds at half size. `sky.test.ts` holds every weather palette to 4.5:1 with its clouds or `FOG_ALPHA` as a white veil, day and night.

## Palettes and contrast

## Conventions

- TypeScript strict. Raw `HTMLElement` with a shadow root, no Lit.
- Update text in place; never rebuild the DOM on a `hass` update. Only re-render when a tracked entity's `last_updated` changed.
- Never put entity data in `innerHTML` without `escapeHtml`.
- Animations: CSS `@keyframes` on `opacity` / `transform` only, paused when hidden or off-screen, none under `prefers-reduced-motion` or `animate: false`.
- Strings: French, English, German, Spanish, Italian, Dutch (`localize.ts` for the card, `LABELS` / `HELPERS` in the editor; tests check every language has every key, `test:browser` that none overflows). Config errors (`configError`) stay French / English. A new string goes in all six.
- All code here is the project's own. Don't copy code from other projects; third-party material (demo icons only, for now) is listed in `NOTICE.md`.
- Work in the phases of the brief (§9); stop after each one for the user's validation.
